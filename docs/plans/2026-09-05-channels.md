# Project Channels — parité Grok Bot pour les group chats
> Statut : **design / exploration**, à valider avant plan d'implémentation détaillé (format writing-plans). Date : 2026-09-05. Sources : docs et guides publics xAI Grok Bot (août–septembre 2026) + cartographie du code. Révision : première version cadrée sur les channels _externes_ (Slack/iMessage) — mauvais objet. Recadré sur `ChatGroup`. L'ancien contenu est conservé en annexe A comme chantier distinct.
## 0. TL;DR
**Ne pas créer de modèle** `Channel`**.** Le concept Grok correspond à un usage particulier des `ChatGroup` existants : un projet, une équipe de bots, un résultat commun. Rakazo en couvre déjà ~80 %, cap 2–6 bots inclus.

Deux écarts réels, tous les deux dans `ChatGroup` :

1. **Aucun objectif persistant.** Un groupe a un nom, pas un résultat attendu. Le kickoff vit dans le premier message du transcript — et la compaction ne tourne **jamais** sur un thread de groupe (`history-compaction.ts:137`). L'énoncé n'est pas résumé : il est tronqué net au 201ᵉ message.
  
2. **Le coordinateur est implicite et arbitraire.** Sans mention, le message réveille `members[0]` (`group-mentions.ts:52-54`), trié par `createdAt` — or tous les membres partagent le **même** `createdAt` (insertion en un `createMany`, `DEFAULT CURRENT_TIMESTAMP` = timestamp de transaction). Le destinataire par défaut n'est pas seulement invisible : il est **non spécifié par SQL**.
  

Scope proposé : **une seule phase**, deux colonnes (`purpose`, `coordinatorBotId`) + injection contexte + routage. Le reste (rename UI, tool `create_channel`, board externe, multi-humain) est écarté en §5 avec les raisons.

## 1. Ce que Grok Bot appelle « channel »
### 1.1 Attention à la source
| Source | Terme employé |
| --- | --- |
| [docs.x.ai — Message and collaborate](https://docs.x.ai/grok-bot/chat-and-collaboration) | **« group »**. Le mot _channel_ n'y apparaît pas |
| [Guide — How I run multiple teams of Grok Bots](https://x.ai/bot/guides/how-i-run-multiple-teams-of-grok-bots) | **« channel »** partout, et « one project equals one channel in the sidebar » |

Le mot « channel » vient donc du **guide d'usage** et du label sidebar, pas du modèle documenté. Le guide précise lui-même : _« Note that this is an experimental pattern I'm still trying out. »_

**Conséquence : on emprunte le pattern, pas le vocabulaire.** Voir §5.1.
### 1.2 Le pattern
- _« One project, one channel, one roster. »_ Un projet = une conversation avec son équipe fixe.
  
- _« Use a group when several Bots need one shared outcome and visible handoffs. »_ (docs) — deux conditions : **résultat partagé** et **handoffs visibles**.
  
- _« Propose at most five bots besides the PM. Each channel is limited at six bots. »_
  
- Adressage : `@Bot` désigne un propriétaire, `@everyone` réveille l'équipe, _« write normally to let the participating Bots decide who should respond »_.
  
- Un **Manager bot** crée le channel, constitue le roster, tient une base Notion, puis _« sits in the channel too, but mostly watches progress »_.
  
- Chaque bot garde sa mémoire spécialisée ; le channel fournit le contexte projet.
  
### 1.3 Ce que Grok n'a pas
Pas de partage multi-humain, pas de RBAC, pas d'invitations, pas d'API Channel. **Le channel n'est pas une frontière de sécurité** — la frontière reste l'utilisateur et son ordinateur. À conserver tel quel : ça évite d'ouvrir le chantier multi-utilisateur (§5.4).

## 3. Écart réel
### 3.1 Pas d'objectif persistant
Le groupe a `name` et rien d'autre. Le résultat attendu, s'il est écrit, l'est dans le premier message du transcript.

Ce que fait réellement le code — pire que « la compaction perd l'énoncé » :

```ts
// history-compaction.ts:135-137
const thread = await deps.prisma.thread.findUniqueOrThrow({ where: { id: threadId } });
if (!thread.botId) return;
```

Un thread de groupe est créé **sans** `botId` (`packages/db/src/groups.ts:263-269`) : la compaction sort immédiatement, à chaque fois. `historyCompactionSummary` reste `null` à vie. Le seul filet restant est la troncature dure `take: LEGACY_HISTORY_WINDOW_SIZE` = **200 messages** (`executor.ts:890`). L'énoncé survit exactement 200 messages puis disparaît d'un coup, sans résumé de repli.

Effet de bord constaté : `executor.ts:3463` enfile `historyCompactJob` sans filtrer sur `groupId` → à partir du 100ᵉ message, chaque run de groupe enfile un job qui sort en ligne 137. Bénin et idempotent, à signaler en PR, pas à corriger ici.

Un champ `purpose` répond parce qu'il entre par un **autre canal** : `groupContext` va dans `instructions` (`executor.ts:2949`), jamais dans `history`. Rien ne le tronque, ni aujourd'hui ni si la compaction de groupe est activée un jour.
### 3.2 Coordinateur implicite
```ts
// group-mentions.ts:52-54
if (targetIds.size === 0 && input.members[0]) {
  targetIds.add(input.members[0].id);
}
```

Trois faits vérifiés qui aggravent le constat :

1. **Le tri ne trie rien.** `createGroup` insère tous les membres via un seul `createMany` dans une transaction (`groups.ts:260-262`) et `createdAt` est `DEFAULT CURRENT_TIMESTAMP` (`0013_group_chats/migration.sql:18`) = timestamp de transaction. Tous les membres ont donc **exactement le même** `createdAt` : `orderBy: { createdAt: "asc" }` est un ex-aequo total, dont SQL ne spécifie pas l'ordre.
  
2. **Toute édition de membres réécrit l'ordre.** `updateGroup` fait `deleteMany` puis `createMany` de _tous_ les membres (`groups.ts:356-361`), dans l'ordre du tableau `botIds` du client = ordre de clic dans le picker. Décocher puis recocher un bot suffit à déplacer le destinataire par défaut. Le retrait n'est pas le seul déclencheur.
  
3. **Second chemin de réveil, avec un bug.** `threads.followUp` branche groupe (`router.ts:1240-1250`) reprend `members[0]` mais **ne filtre pas** `bot: { archivedAt: null }`, contrairement à tous les autres chemins : il peut réveiller un bot archivé. Aucun client ne l'appelle avec un `groupId` aujourd'hui, mais l'endpoint est exposé.
  

Le handoff bot→bot ne partage **pas** ce fallback : `handoffToGroupBot` exige une cible explicite (`group-handoff.ts:90`) et refuse non-membres, soi-même et renvoi à l'expéditeur. Rien à y changer.

Grok laisse _les bots_ décider qui répond ; rakazo prend la décision hors du modèle, sur un critère qui n'a aucun sens produit. Rendre le choix explicite est plus simple que de rendre la décision autonome, et corrige le même symptôme. Voir §5.6 pour le chiffrage de l'alternative Grok.

## 4. Phase 1 — Project Channel core
**Seule phase en scope.** Estimation : 1,5 à 2 jours. Les deux champs ne sont pas structurellement couplés, mais touchent les mêmes fichiers : **une seule migration** (deux `ADD COLUMN` sur `chat_groups`) et `purpose` livré en premier pour fixer la convention de rendu.
### 4.1 Modèle
```prisma
model ChatGroup {
  // …
  purpose          String  @default("")   // résultat attendu / definition of done
  coordinatorBotId String?                // réveillé quand aucun membre n'est mentionné
  coordinator      Bot?    @relation("ChatGroupCoordinator", fields: [coordinatorBotId], references: [id], onDelete: SetNull)
  @@index([coordinatorBotId])
}
```

- `purpose` : **champ libre**, pas de template à trois cases. `GROUP_PURPOSE_MAX_LENGTH = 2000`. Optionnel : un groupe sans objectif se comporte comme aujourd'hui.
  
- `coordinatorBotId` **nullable en base, non-null garanti par le repo**. Nullable est imposé par la migration (colonne ajoutée avant d'être remplie) et par `detachBotFromGroups` (`child-bots.ts:455-555`), où un `NOT NULL` transformerait une suppression légitime en erreur. Même choix que `chat_group_members_botId_fkey` : l'invariant vit dans le repo.
  
- `onDelete: SetNull` (et non `NoAction`) : la nullité est récupérable au runtime via le repli §4.2, un membre manquant ne l'est pas.
  
- Migration en deux passes, **avant** l'ajout de la FK : (1) `DISTINCT ON (groupId)` sur les membres non archivés, `ORDER BY createdAt ASC, id ASC` — reproduit la cible actuelle ; (2) même requête sans le filtre `archivedAt`, pour les groupes entièrement archivés.
  
- **Limite honnête** sur le tie-break `id ASC` : les `createdAt` étant tous égaux (§3.2), il n'y a pas d'ordre pré-migration à préserver. La migration transforme un comportement _non spécifié mais observé comme l'ordre d'insertion_ en un comportement _spécifié comme l'ordre d'insertion_. Aucune option strictement conservatrice n'existe. Second écart assumé, à écrire en description de PR : un groupe dont le doyen est archivé revient aujourd'hui à ce bot au `restore` ; après migration le coordinateur backfillé reste en place.
  

Invariants du coordinateur

| Événement | Règle |
|---|---|
| `createGroup` | `coordinatorBotId ?? botIds[0]`. `IsolationError` si ∉ `botIds` |
| `updateGroup` | Coordinateur effectif = `input.coordinatorBotId ?? current`. **Rejet** s'il ∉ membres résultants |
| `groups.duplicate` | Recopier `source.coordinatorBotId` — sinon silencieusement perdu |
| Bot **archivé** | Rien. Le repli runtime prend le relais, `bots.restore` rétablit sans action utilisateur |
| Bot **supprimé** | Réassignation au doyen restant, dans la transaction `detachBotFromGroups` — la suppression n'est pas refusable |
| `archiveGroup` / `removeGroup` | Rien |

**Retrait du coordinateur : rejet, pas réassignation.** Une réassignation auto _est_ un déplacement silencieux du destinataire — exactement ce qu'on corrige. Le rejet coûte un `if` et zéro règle d'ordre à figer. Friction nulle en pratique : le radio et le picker sont dans le même formulaire, l'UI ne laisse pas produire l'état invalide. Seule exception : la suppression définitive d'un bot, où le rejet n'est pas une option offerte.
### 4.2 Routage
Cascade exacte, arrêt au premier niveau qui produit une cible :

1. Chips de mention explicites, filtrées aux membres (`group-mentions.ts:39-42`).
  
2. `@everyone` → tous les membres actifs.
  
3. `@Nom` par membre.
  
4. **Coordinateur**, s'il est présent dans `members`. `members` est déjà filtré `bot: { archivedAt: null }` en amont (`thread-target.ts:245`) : coordinateur archivé ⇒ absent ⇒ ce niveau échoue sans requête supplémentaire.
  
5. `members[0]` — doyen des membres actifs, ordre `(createdAt, id)`. Couvre coordinateur archivé, `NULL`, ou `SetNull` concurrent.
  
6. Aucun membre actif : inatteignable, `lockAndLoadGroupMembers` lève déjà `IsolationError` avant toute écriture (`thread-target.ts:252`).
  

Signature rétro-compatible : `coordinatorBotId?: string | null` optionnel, absent ⇒ comportement identique à aujourd'hui. **Aucun run perdu** : le niveau 5 est total.

`threads.followUp` (`router.ts:1240-1250`) applique la même cascade en local (un seul bot, ni texte ni mentions à parser) — et gagne au passage le filtre `archivedAt` manquant (§3.2, point 3).
### 4.3 Contexte
`renderGroupMembersContext()` (`bot-messages.ts:114`) reçoit `purpose` et l'émet dans un bloc délimité `<group_purpose>`, **avant** le roster. `loadGroupContext` (`group-handoff.ts:190`) sélectionne le champ.

- Échappement : `escapePromptData`, **pas** `escapeDirectoryField` — ce dernier convertit les vrais retours à la ligne en `\n` littéraux et détruirait la mise en forme d'un texte multi-lignes.
  
- Cap appliqué **après** échappement.
  
- **Pas** marqué _untrusted_ : vérifié, aucun outil d'agent n'écrit dans `chatGroup` ; le seul chemin d'écriture est `updateGroup`, sous `authed` + `lockOwnedGroup`, donc saisi par le propriétaire. Le marquer untrusted affaiblirait le signal là où il est justifié (le roster).
  
- **Le coordinateur n'entre pas dans le prompt.** `bot-messages.test.ts:221-222` interdit explicitement au roster de nommer un orchestrateur (`not.toContain("Chief of Staff")`, `not.toContain("orchestrator")`, cf. `3b510e01`). Le coordinateur est une règle de routage **backend** pour les messages de l'utilisateur ; l'injecter recréerait la hiérarchie de bots que le produit a refusée, et transformerait un bloc marqué _untrusted routing metadata_ en porteur d'instruction de commandement. Zéro ligne, zéro copie de prompt, un test existant préservé.
  
### 4.4 Surface
- Création : nom + objectif + 2–6 bots + coordinateur (présélectionné sur le premier choisi).
  
- Édition dans les réglages existants du groupe. Aucun nouvel écran.
  
- Copie visible ajoutée, à citer en description de PR (exigence AGENTS.md) — deux chaînes, pas une de plus : label `Goal` + placeholder `What this group should deliver` pour `purpose` ; label `Answers when unmentioned` pour le groupe de radios coordinateur. Sans ce dernier, l'utilisateur voit deux contrôles par ligne sans savoir ce que le second décide : c'est le nom du contrôle, pas de l'explicatif.
  
- Révélation progressive : le radio coordinateur n'apparaît que sur les lignes **sélectionnées**. Web = `<input type="radio">` à la place du `<Check>` ; mobile = ligne pressable + coche à gauche du `Switch` existant (`bot-member-picker.tsx`), pas de second contrôle sur la ligne.
  
- Décocher le coordinateur dans le formulaire déplace le radio vers un autre membre sélectionné : l'état que le serveur rejette n'est pas atteignable par l'UI.
  

**Deux pièges vérifiés, à ne pas rater :**

- `router.ts:977-982` — `groups.duplicate` reconstruit `{ name, botIds }` à la main : sans ajout explicite, il **perd silencieusement** `purpose` et `coordinatorBotId`.
  
- `apps/mobile/app/group-settings.tsx:49` — garde `if (input.name || input.botIds)` : falsy-cassée pour effacer un champ. Passer à `Object.keys(input).length > 1`. La comparaison de membres y est aussi sensible à l'ordre (`selected.join(",")`), contrairement au web (`sameMembers`) : à aligner, l'ordre cesse de porter du sens.
  
- Zod : les `.refine()` cross-field sur `CreateGroupInput` / `UpdateGroupInput` les font passer de `ZodObject` à `ZodEffects` — casse tout `.extend()` en aval. Si c'est le cas, porter la validation croisée entièrement dans le repo.
  

Fichiers : `packages/contracts/src/domain.ts`, `packages/db/src/groups.ts`, `packages/core/src/{group-mentions,bot-messages}.ts`, `packages/adapters/src/{group-handoff,child-bots}.ts`, `apps/api/src/{thread-target,router}.ts`, `apps/web/src/pages/GroupPanel.tsx`, `apps/mobile/{components/bot-member-picker.tsx,app/new-group.tsx,app/group-settings.tsx,lib/api.ts}`.

## 5. Écarté, et pourquoi
### 5.1 Renommer « Group » en « Channel » dans l'UI
**Non.** `MessagingChannel` est déjà exposé à l'utilisateur (`MessagingSettingsOverlay.tsx`) et désigne une vraie conversation externe. Appeler « Channel » le group chat interne déplace l'ambiguïté du code vers l'utilisateur, qui lui n'a aucun moyen de la lever. AGENTS.md : _« Treat every visible word as UI. Start UX work by asking what can be removed. »_ Le gain serait l'alignement sur le vocabulaire d'un billet expérimental d'un autre produit (§1.1). « Group » reste.
### 5.2 Tool `create_channel` pour un Manager bot
**Différé.** Spéculatif tant que la phase 1 n'a pas d'usage mesuré : rien ne dit que la friction est à la création plutôt qu'au cadrage. Si le besoin apparaît, l'interface est évidente (`{ name, purpose, coordinatorBotId, botIds }`, bots existants du même user + même space, validation humaine obligatoire, jamais de création de bot ni d'installation de connecteur) — mais on l'écrira à ce moment-là, avec le signal.
### 5.3 Board de tâches / automatisations
**Différé.** Le pattern Grok s'appuie sur Notion _externe_. Ne pas écrire de task manager rakazo avant d'avoir prouvé que transcript + connecteur ne suffisent pas.
### 5.4 Multi-humain dans un channel
**Hors scope, et Grok ne l'a pas non plus.** `ChatGroup`, `Thread`, `Task` et `Run` sont liés à un `userId` unique (`schema.prisma:400-454`) : ce serait un chantier de plusieurs semaines et une frontière d'autorisation à redessiner. Sans rapport avec le concept visé.
### 5.5 Fusionner `ChatGroup` et `MessagingChannel`
**Hors scope.** Deux problèmes distincts. Voir annexe A.
### 5.6 Laisser les bots décider qui répond (le pattern Grok)
**Non.** Deux implémentations possibles, aucune gratuite. _Tout le monde lit, chacun décide de se taire_ : jusqu'à 6 runs par message non adressé (`GROUP_MEMBER_MAX = 6`), 6× le coût modèle et l'occupation d'écran, et rien ne garantit qu'exactement un bot parle — zéro réponse = run perdu. _Un round de routage puis le travail_ : +1 aller-retour de latence et il faut un bot pour tenir le round, c'est-à-dire un coordinateur implicite et non éditable — le problème de départ, avec la facture en plus.

Le coordinateur explicite **subsume** le round de routage : il en est le résultat, mis en cache, visible et éditable. L'inverse est faux. Et le cas où l'utilisateur veut vraiment que tout le monde réponde est déjà couvert, gratuitement, par `@everyone`.

## 6. Tests bloquants
1. Sans mention, seul le coordinateur est réveillé.
  
2. `@Bot` et `@everyone` gardent leur comportement actuel, coordinateur compris.
  
3. Retirer le coordinateur impose d'en désigner un autre ; sinon rejet `IsolationError` **et aucune écriture** (`chatGroupMember.deleteMany` jamais appelé).
  
4. Coordinateur archivé → repli sur le premier membre vivant, aucun run perdu.
  
5. Réécrire `botIds` avec les mêmes ids dans un ordre différent laisse `coordinatorBotId` **inchangé** — test de non-régression central.
  
6. `threads.followUp` sur un groupe réveille le coordinateur, et **ne réveille pas** un doyen archivé (régression du bug §3.2).
  
7. `purpose` présent dans le contexte de chaque bot du groupe, multi-lignes préservé, cap appliqué après échappement.
  
8. `groups.duplicate` conserve `purpose` et `coordinatorBotId`.
  
9. Migration (test Postgres) : trois groupes seedés — `createdAt` distincts, batch unique, doyen archivé. Capturer la cible pré-migration, asserter l'égalité après. Documenter dans le test que le cas « batch unique » était non spécifié avant.
  
10. Création et édition fonctionnent sur web et mobile. Pas de suite e2e mobile dans le repo : extraire la logique « décocher le coordinateur déplace le radio » en fonction pure `@rakazo/core` testée une fois, ou dégradation explicite en description de PR.

## Annexe A — Channels externes (`MessagingChannel`), chantier distinct
Constats de la première version du document. Toujours valides, mais ils répondent à « où le bot peut-il vivre » et non à « comment une équipe de bots mène un projet ».

- **Un seul provider fait les groupes.** `capabilities.groups: true` pour sendblue uniquement ; Slack, WhatsApp, Telegram à `false` — commentaire explicite `messaging-platforms.ts:52` : _« Group conversations stay sendblue-only until channel semantics are mapped for the other platforms »_. Le contrat manquant tient en trois hooks : `participants`, `channelName`, `isDM`.
  
- **Réveil non adressé.** Un message humain réveille **tous** les bots approuvés du channel (`messaging-inbound.ts:445`). Le filtre `@mention` n'existe que pour le trafic bot→bot (`messaging-delivery.ts:189`). Coût et bruit linéaires au nombre de membres — bloquant pour un channel Slack public.
  
- **Pas de fil partagé.** Chaque bot vit la conversation dans son propre thread, préfixé `[Group "x", Alice]:`. Aucun `Thread` ne représente le channel externe.
  

Si ce chantier est ouvert un jour, l'adressage explicite est un **prérequis** de l'ouverture à Slack, pas une suite.

## Questions ouvertes
1. `purpose` ~~: champ libre ou template ?~~ **Tranché : champ libre**, cap 2000. Un template à trois cases impose une structure à des projets qui n'en ont pas tous une, et produit des cases vides interpolées dans le prompt.
  
2. ~~Coordinateur visible dans la liste latérale ?~~ **Tranché pour le prompt : non** (§4.3). Reste ouvert pour la sidebar UI — probablement non, la révélation progressive suffit.
  
3. Faut-il un kickoff prérempli au premier message, ou est-ce du texte imposé que l'utilisateur effacera ?
  
4. Annexe A : chantier à ouvrir, ou statu quo assumé et documenté ?
  
5. Le job de compaction mort sur les threads de groupe (§3.1) : ticket séparé, ou simple garde `if (thread.groupId) return` ajoutée en passant ?
