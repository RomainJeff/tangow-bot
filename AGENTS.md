# AGENTS.md

- Desktop and mobile releases use Home Assistant style calendar versioning, `YYYY.M.PATCH`, with an unpadded month. Version each client independently from its changes since its last release: the first changed release in a calendar month is `YYYY.M.0`, and subsequent changed releases increment the patch. An unchanged client keeps its version; never decrease or reuse an already reserved version for a new changed release. Features and breaking changes belong in release notes, not SemVer major or minor bumps. Keep the iOS marketing version separate from EAS-managed incrementing build numbers. Use `.agents/skills/release/SKILL.md` for version updates, builds, submission, and publication.
- This is a public repository: assume all tracked content and diffs are public. Never commit secrets, `.env` files, private URLs, personal/customer data, or real production data; use fake placeholders. Review `git status` and the staged diff before committing, and never force-add ignored files. If private data appears, stop and alert the maintainer.
- Rakazo is one product across web, Electron desktop, and Expo mobile; Electron hosts the web UI. Put shared behavior, contracts, API logic, and reusable UI in packages. Keep only genuinely native navigation, storage, permissions, and interactions platform-specific. Core workflows must cover every applicable surface or degrade safely for an explicit reason.
- No hosted vendor is required to run the core product. Keep LLMs, sandboxes, memory, voice, integrations, and future external services optional and behind provider-neutral interfaces. Vendor SDKs, configuration, and translation belong only in adapters and composition roots. New providers must reuse shared contracts and deterministic offline conformance tests.
- Keep UI and copy minimal. Show advanced capability progressively and only when it becomes relevant; do not add explainer text that repeats the interface. Frontends express intent and render state; the backend owns orchestration, authorization, validation, retries, recovery, and provider translation. Give controls concise accessible names when needed.
- Treat every visible word as UI. Start UX work by asking what can be removed, and prefer progressive disclosure over persistent explanation or status chrome. If a PR adds user-facing copy, its description must quote the copy, explain why it is necessary, and say why removing it or revealing it only when relevant would not work.
- Configure compatible providers and models through shared connection settings and standard protocol capabilities; never add provider- or model-specific environment variables when the generic connection can express the behavior.
- Skills versioned in `skills/` (the `agent` family for the bot harness, `computer` for coding agents on the computer) are documented in `skills/README.md`; read it before adding one.
- Use top-level `import type`, never inline type imports. Reserve dynamic `import()` for necessary deferred loading.
- Keep code simple: reuse existing primitives and one source of truth, remove duplication and unused flexibility, and avoid speculative abstractions. Add an interface when it protects a real external or platform boundary, not for its own sake.
- Before adding complexity for a speculative or vanishingly unlikely race or security edge case, explain the concrete failure mode, likelihood, and complexity cost to the user and get their buy-in. Do not silently expand scope for theoretical robustness.
- Every new implementation plan, architecture proposal or multi-ticket breakdown, including automatically generated plans, gets an independent `founding-engineer` review before presentation or execution. Follow the plan-review protocol in `.agents/skills/principle-laziness-protocol/SKILL.md`. Progress checklists are not new plans. The reviewer reports advice without editing the plan; the plan owner exposes the findings and records their disposition. This adds no human approval gate.
- Parallel delegated tasks coordinate through their launching orchestrator using `.agents/skills/poteto-mode/references/coordination.md`. Workers report cross-task discoveries before changing shared assumptions or scope; the parent relays decisions and obtains acknowledgement from affected active workers. Verify results against the current brief before integration.
- Treat auth, secret handling, sandbox boundaries, host commands, and integrations as security-sensitive. Keep tests deterministic and offline by default.
- The desktop Playwright suite (`pnpm --filter @tangow/desktop test:e2e`) opens real Electron windows and steals focus on macOS. Do not run it on a maintainer's machine as routine verification; run the unit tests locally and let CI's virtual-display job run the e2e on push.
- Right after creating a pull request, run the `merge-risk` skill on it and post its output as a PR comment. After creating a pull request, stay with it until CI and automated review bots have finished; passing checks alone do not mean the review is complete. Wait for the checks on the current head commit to be terminal with a single backgrounded call (e.g. `gh pr checks --watch`). Do not poll in the foreground on a timer, which mostly buys repeated snapshots of an unchanged PR and dies at the tool timeout. Triage review feedback by concrete impact before changing code. Fix only issues that materially affect correctness, security, reliability, a core user flow, or an explicit requirement of the change. A suggestion being actionable is not enough: do not expand scope for style preferences, speculative risks, optional refactors, or minor improvements. Briefly dismiss or defer those suggestions with a reason; important issues unrelated to the change should be reported separately unless they block safe delivery. Push necessary fixes and repeat only while material issues remain or new checks or reviews are pending. Do not merge while review bots are still pending or material issues remain unresolved; dismissed or deferred suggestions do not block completion.
- Use a feature branch only for one large feature whose slices depend on each other and only make sense together; changes that are unrelated or can each ship on their own go straight to `main` as separate PRs, however many there are. Such a feature goes through a feature branch: create `feature/<name>` from `main`, open its PR to `main` as a draft once it has its first commit, then branch each slice from the feature branch and open it as a small PR targeting that branch. Keep the feature PR description current: under a `## Sub-PRs` heading, list every slice PR as a task item (`- [x]` merged, `- [ ]` open or planned) with its link and a one-line summary, and update it whenever a slice PR is opened, merged, or dropped. Merge slices into the feature branch once their own CI and review are done, keep the feature branch up to date by merging `main` into it (never rebase or force-push it), and once every slice is in and the full feature works, mark the feature PR ready for review (drafts get no bot review) and merge it after that review. The `CHANGELOG.md` entry lands once, in the last slice, dated for the day the feature PR merges.
- PR descriptions say why the change exists, what changed, and how it was tested. Write Why as the product reason (what was wrong and what this changes); never "Elie wants" or a third-person briefing of a named person; the maintainer is the author.
- Every change that a user can observe updates `CHANGELOG.md` in the same PR (for a feature branch, see above), never in a sweep afterwards. Entries go under `## [Unreleased]` in a `### YYYY-MM-DD` section for the day the work lands, newest day first, split into `#### Added` / `#### Changed` / `#### Fixed` / `#### Reverted` and only the headings that have content. Write the outcome for the person using Rakazo, not the mechanism: what they can now do, on which surfaces, and what it replaces. An Added entry opens with a bold sentence naming the capability, then one or two sentences of concrete detail; Changed and Fixed entries are one sentence. One entry per user-visible outcome, not per commit — a feature built over ten commits or four phases is a single entry on the day it becomes usable. Leave out what a user cannot observe (docs, plans, tickets, refactors, build and CI work, formatting, dependency bumps) and drop the day heading entirely when nothing user-visible shipped. A feature that shipped and was pulled back goes under Reverted rather than being deleted. Link a relative doc path when the feature needs setup.
- Commit messages, PR descriptions, issues, and review replies are public too. Describe test results in words instead of pasting tool output, and never include anything that identifies a person, machine, or account: local paths, usernames, hostnames, signing identities, legal entity names, Apple Team IDs, API key IDs, issuer or tenant IDs, account emails, or the accounts, machines, and files that secret values came from. Naming the secrets a workflow reads is fine; use placeholders when a value must be shown.
- CI does not run the web E2E suite, so every change validates the feature scope it touches: before pushing run `pnpm test:e2e:affected`, which runs the specs the change reaches and switches to the full suite itself when shared plumbing changes or a changed runtime file is reached by no spec; run the full `pnpm test:e2e` only when it asks to or to rerecord the impact map. Update the specs in `apps/web/e2e/` whose behavior changed in the same change (see the README). When the selector reports a file no spec reaches, judge hard whether it deserves an e2e: add one only for a user-visible flow that no unit test can prove, never a test for the sake of coverage. Whenever a change adds or edits tests, run the `test-audit` skill and remove what it finds low-value. For every user-visible change, capture the feature on each surface it touches and post the screenshots in the PR: desktop and phone width from the web E2E (`captureScreenshot` at the default viewport and at 390x844), and the native iOS app with `pnpm test:mobile-screenshots` when mobile is touched. Add the spec or Maestro flow that opens the screen if it is missing; if a surface cannot be captured, say why in the PR.
- UI system. `docs/design-system.md` is the living reference for the Quiet skin: a screen never defines a color, size, radius, shadow or duration by hand, it composes tokens and primitives from `@tangow/ui-web`. Colors live in `@tangow/ui-tokens` as semantic tokens (background, card, muted, border, primary, destructive, ...) with one TypeScript source that generates `tokens.css`; never hardcode a product hex or use `[var(--…)]` arbitrary values. Web and Electron use shadcn/ui on Base UI, vendored into `packages/ui-web` via `pnpm exec shadcn add` from the official registry only (third-party registries are a supply-chain risk); reuse those components before writing chrome by hand, and reuse `apps/web/src/components/ai/` for AI moments (loading, shimmer, success). The app is monochrome: primary is ink, status colors are destructive/success/warning, bots carry the only identity color. Mobile is native-first: Expo Router, Expo UI, native sheets, menus, alerts and pickers wherever one exists; custom surfaces (thread, composer, avatars, cards) use plain StyleSheet with the shared tokens through `apps/mobile/lib/appearance`, and system chrome stays PlatformColor via `lib/native`. Mobile may diverge from web when the native pattern is better.
